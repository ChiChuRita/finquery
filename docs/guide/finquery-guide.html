Everything behind the four electives and the fine-tuned models, in the order a grader will ask about it. Every claim here points at a file. Read it top to bottom once, then use the quiz at the end.

The one rule. Numbers come from executed queries, never from the model. The model writes the question and the words; a guard checks; SQLite writes the numbers. Foundations: how the pieces are wired

Pydantic AI, the way FinQuery uses it

Pydantic AI is the agent framework. It gives us four things and we build the rest ourselves, which is what the course rule about libraries requires.

The local runtime

llama-cpp-python runs in the server process. Two seats: the chat seat holds Gemma 4 12B (or Qwen3.5 9B if the user picks it), the fast seat holds Gemma 4 E4B, always resident, where adapters attach. Both at 32k context, about 12.9 GB together. Our LlamaCppModel (src/finquery/local/model.py) translates Pydantic AI messages into the model's chat template, forces the tool grammar for a sub-agent call, and parses the Gemma tool-call syntax back (src/finquery/local/gemma.py). Sub-agents always run with reasoning off and a 3,072-token ceiling.

A real bug we found here. llama.cpp passes raw line breaks inside the JSON of a tool call. A fine-tuned model that writes SQL over several lines therefore produced invalid JSON and every answer failed validation. normalize_json_arguments now re-serializes the arguments before validation. Vanilla models escape their line breaks, so only the adapters were hit.

The model catalog and the per-role setting

Four entries: Gemma 4 12B (local, default), Gemma 4 26B (cloud), Qwen3.5 9B (local), Qwen3.5 9B (cloud). The chat runs on the conversation's entry. Every sub-agent role has its own setting, FINQUERY_SUBAGENT_MODEL_<ROLE>: chat (the default, the conversation's model), fast (the E4B seat, where adapters attach), or a pinned catalog key. In the demo every role runs on the 12B; set the query role to fast and it runs on E4B with the query adapter.

Elective 1: intelligent context management

The fence around what the model may see. The sheet asks for isolation, selection and compression. All three are separate mechanisms in code.

sequenceDiagram participant U as User participant API as api/chat.py participant C as context.py participant M as memory.py participant F as fast model participant Chat as chat model U->>API: message API->>M: build_memory_block(profile, message) M-->>API: up to 5 facts selected by keyword overlap API->>C: assemble(turns, summary, summary_through, memory) C-->>API: instructions = summary note + memory block; history = turns after the divider API->>C: needs_compression(assembly, budget)? alt tokens above 60 percent of 32k API->>F: summarize(older turns) F-->>API: summary text API->>API: store summary, move the divider end API->>Chat: run(history, instructions, tools that apply) Chat-->>U: answer API->>F: distill facts from the finished turn F-->>M: at most 2 durable facts, no figures

Isolation

A profile is a workspace: transactions, accounts, categories and rules, conversations, memory, the web lookup cache and journal, dashboard cards, all carry a profile id. The enforcement is not a prompt. Every SQL query the model writes runs against a temporary view created for that request with the profile id inlined in the WHERE clause, on a read-only connection (src/finquery/query/guard.py, execute_read_only). Even a perfect injection could only read this profile's rows.

CREATE TEMP VIEW transaction_view AS
  SELECT * FROM main.transaction_view WHERE profile_id = '<this profile>'
PRAGMA query_only = ON
-- the model's statement runs here, then the view is dropped

Selection

Per turn, context.assemble builds exactly: the memory block (MAX_MEMORIES = 5 facts chosen by keyword overlap with the message, select_memories), the rolling summary if one exists, the turns after the divider (RECENT_TURNS = 6 as the default window), and only the tools that apply. Web lookup is not declared to the model when the profile has it off (_only_when_web_lookup_is_on in agent.py): the model cannot call what it cannot see. The header badge shows the estimated tokens against the budget; estimate_tokens counts the same text the model is sent.

Compression

COMPRESS_ABOVE = 0.6: when a turn would cross 60 percent of the window, the turns before the divider are folded into a summary by the fast model (summarize, capped at MAX_SUMMARY_CHARS = 4000), before the answer runs, so the turn that crosses the threshold already runs small. The divider is a visible, editable line in the transcript. A pending Question card is never summarized away, because the run could not resume from it.

Memory (the required "project folder" memory)

After every turn a memory sub-agent (remember_facts, forced tool) distills at most MAX_DISTILLED = 2 durable facts. Its instructions say what durable means, and code enforces it again (is_durable): never a number or a total, never a one-off order ("recategorize all Netflix rows" is not a rule; "Netflix is always Leisure" is), and never a name that did not appear in the user's own words (absent_names). The Memory page lists and edits facts; a new chat in the same profile recalls them.

# src/finquery/memory.py, DISTILL_INSTRUCTIONS (excerpt)
You keep the long-term memory of a personal-finance assistant.
You are given one finished exchange. Call `remember_facts` exactly once with the durable facts
it establishes: what a merchant or a counterparty is, a rule the user stated ("PayPal to Anna
is always dining"), a preference, a goal, or a constraint that will still be true next month.
Returning an empty list is the normal case and always allowed. Never keep a number or a total
(those come from queries and go stale), a one-off question, small talk, ...

Elective 2: sub-agent deployment

The fence around what the model may do. A sub-agent is a tool whose handler runs its own model call with its own prompt and schema, then checks the answer with code.

sequenceDiagram participant Chat as chat agent (12B) participant T as tool `query` (Python) participant P as query_prompt (code) participant S as query sub-agent participant G as SQL guard participant DB as SQLite participant J as check pass Chat->>T: query(request="groceries in May 2025") T->>P: build prompt: schema, rules, 9 examples, household facts, question T->>S: run, forced tool run_sql S-->>T: {reasoning, sql} T->>G: validate_sql (sqlglot, one SELECT, view only, LIMIT, no CASE classifier, no cents) G-->>T: ok, or a sentence back to S once T->>DB: execute_read_only on the profile view DB-->>T: rows T->>J: judge_result(question, sql, rows) J-->>T: ok, or revise with the intent (one rewrite) T-->>Chat: rows, columns, sql, figures (data, not prose) Chat-->>Chat: writes the answer; prose figures are verified against the rows

The pattern, identical for all six

  1. The chat agent decides a tool is needed and writes the request in words.
  2. Code builds the sub-agent prompt: rules, worked examples with reasoning before the answer, the household's facts (data range, categories, busiest counterparties). The chat agent never writes this prompt.
  3. The sub-agent answers through a forced tool schema whose first field is reasoning. It commits to its plan before the answer.
  4. A check that is code: the guard and execution for SQL, the self-check on the real rows for charts, the two extraction guards, the no-figures rule for memory, the floors and the verbatim quote for web lookup. A finding goes back once, word for word.
  5. The result returns as structured data. Every step streams into the transcript as a chain of thought (ctx.deps.narrate).

The query sub-agent in full

# src/finquery/query/subagent.py, INSTRUCTIONS (the system prompt)
You write SQLite queries over one household's bank transactions. You are given a question and
the shape of the data. Call `run_sql` exactly once.
Fill `reasoning` before you write any SQL: one short line each for the period you read out of
the question, the filters, the sign, and the grouping. Then write `sql` so that it does exactly
what those lines say. You never explain yourself outside that field, never apologize and never
answer the question in words: the SQL is the answer.

The user message is built by query_prompt(request, context), about 2,850 tokens: the view's columns with one line each, the rules (below), nine worked examples in both languages with their reasoning lines, the household paragraph (newest booking, what "this month" and "last month" mean, the categories, the busiest counterparties), and the question. The model sees no rows.

# RULES (excerpt)
- One statement, a single SELECT. No INSERT, UPDATE, DELETE, CREATE, DROP, ATTACH or PRAGMA,
  no other table or view, and never a schema prefix such as main.
- Aggregate. At most 200 rows come back (a LIMIT is added for you) ...
- Spending is negative. For a spending question filter `amount < 0` and report a positive figure
  with `ROUND(-SUM(amount), 2)`. Income is `amount > 0`.
- `amount` is in euros and is the only column a figure may come from. There is no cents column
  to divide, so never write anything like `/ 100`.
- The category of a booking is the `category` column and nothing else. Never write a classifier:
  a `CASE WHEN description LIKE '%rewe%' THEN 'Groceries'` invents labels the household never
  chose, and the guard refuses it. Group by `coalesce(category, 'Needs review')` ...

The guard (validate_sql): parsed with sqlglot; exactly one SELECT; only transaction_view; no schema prefix; a LIMIT of 200 added; refuses a CASE that invents categories, cents in the projection, a subcategory used as a category, more than eight LIKE terms, CROSS JOIN, statements over 1,500 characters. The check pass (query/check.py): code first names degenerate results (no rows, all NULL, a lone zero on something the household has), then a second forced-tool call judge_result answers ok or revise with the intent in words, never SQL; one rewrite follows. Three model calls at most per question.

# src/finquery/query/check.py (excerpt)
You judge whether a SQL result answers the question a household asked about its own bank
transactions. You never write SQL, you never state a figure and you never answer the question
yourself. Call `judge_result` exactly once.
Answer `ok` when the statement asked what the question asked. A small, an empty or a surprising
result is still ok when the statement is right: the data is allowed to hold no answer.
Answer `revise` when the statement answers a different question. ...

The chart sub-agent: two passes and a sandbox

Plan pass (chart_plan): language from the request alone, shape from a menu of eight (line, area, bar, bar_horizontal, bar_grouped, bar_stacked, doughnut, sankey; line and area may carry several series), a caption, and the data question with the exact columns. The plan's question then goes through the query path above, so chart rows are guarded rows. Code pass (chart_code): the body of one JavaScript function over an allowlist of globals (below), given a brief of the real columns and rows. Self-check (chart/selfcheck.py): the code is run in-process against stubs of the same globals on the real rows; rules such as "euro axis holds zero", "one series needs no legend, several need one", "no more than six series", "every named column exists" become repair findings; up to three attempts; failures are visible in the transcript. The frame: a sandboxed iframe with TanStack Charts and the house theme; the model never touches the DOM, and rules like square corners live in the frame, so a stored dashboard card takes a new look without regeneration.

Elective 3: multimodal ingestion

The fence around what the model may read. A vision model reads pages and receipts, and no figure it returns is trusted unless code finds it in the source.

flowchart LR F[file: PDF, photo, CSV, XLSX, DOCX, text] --> R{text layer or table?} R -- yes --> T[text or rows] R -- no --> I[render page to image, EXIF rotate] T --> X[extraction sub-agent, one page per call] I --> X X --> V[verbatim guard: every amount and date occurs in the source] V --> Q[reconciliation: opening + bookings = closing] Q -- flagged --> RC[review card, nothing written] Q -- clean --> D[duplicates asked one by one] D --> C[categorizer, Question cards] C --> DB[(transactions)] style X fill:#1e2a44,stroke:#7aa2f7 style V fill:#2a2412,stroke:#f5b942 style Q fill:#2a2412,stroke:#f5b942
  • Routing (extract/statement.py, ingest/chat_import.py): a PDF with a text layer is read with pdfplumber; scans and photos are rendered with pypdfium2 or opened as images, EXIF-rotated first (the real Edeka receipt was sideways). CSV and XLSX (openpyxl, cells keep their types) go to the mapping engine with presets for Sparkasse and Trade Republic, otherwise the model proposes a column mapping the user confirms. DOCX (python-docx) becomes text for the same path as pasted text.
  • Extraction sub-agent: Gemma 4 with its vision projector, one page per forced-tool call, four pages concurrently locally. It returns rows with the amount and date as printed.
  • Verbatim guard (extract/guards.py, occurs, date_occurs, _verbatim): every amount and date must literally occur in the page text, or in the span the model quoted from the image. The model points at digits; code adds the year; a digit the source does not contain is a refusal, not a correction.
  • Reconciliation (Reconciliation): opening balance plus the sum of bookings equals the closing balance to the cent. A gap flags the page.
  • Review card: flagged rows show the row, the gap and the printed line; nothing is written until the user accepts. Clean pages import, then every possible duplicate is asked about (ingest/duplicates.py), and the categorizer files what it can.
  • Receipts (extract/bill.py): a photo becomes a draft booking with item legs (a split) and the store resolved from the header through the dictionary or, with the switch on, one web lookup.

Measured: 19 of 19 receipt totals right on the real receipt and 18 web receipts (.scratch/finquery/reviews/receipts-web-2026-09-05.md); the synthetic statement PDF reconciles to the cent in the tests; the Excel export imported 433 of 433 rows with the preset recognized without a model call (ticket 58). Not covered: audio.

Elective 4: self-controlled web search

The fence around what may leave the machine. The model decides its own searches and page reads, must quote the page it read, and only a scrubbed merchant token ever goes out.

flowchart TD B[booking text and counterparty] --> S[scrub: legal form wins, given-name list refuses, two-word rule] S -- refused: a person --> N[nothing leaves, household is asked] S -- token, e.g. sixt --> L{decide: search, fetch, finish} L -- search, max 4 --> W[ddgs: duckduckgo, bing, brave] W --> J[(journal, written before the request)] W --> L L -- fetch, max 3 --> P[one GET, 10 s, 300 kB, same-host redirect only] P --> J P --> L L -- finish --> E[evidence quote must occur verbatim in what was read] E --> K[confidence capped at 0.6 unless a source names the token] K --> C[(cache per profile)] style L fill:#1e2a44,stroke:#7aa2f7 style S fill:#2a2412,stroke:#f5b942 style E fill:#2a2412,stroke:#f5b942 style K fill:#2a2412,stroke:#f5b942

Scrubbing (weblookup/scrub.py)

Order matters and is tested: a legal form anywhere (GmbH, AG, SE, KG, e.V., a.G., eG, B.V., Ltd, "& Co") decides business; then a list of the two hundred most common German given names refuses anything that reads like a person in either word order ("ANNA WEBER", "Weber Anna"); then the two-capitalized-words rule. "Sixt GmbH & Co Autovermietung KG" becomes sixt; "Metzgerei Huber" passes as a business; a PayPal transfer to a friend is refused. Amounts, dates, IBANs and reference numbers never enter the token. safe_query checks the model's own search query against the same rule.

The loop (weblookup/loop.py, run_loop)

Budgets: MAX_SEARCHES = 4, MAX_FETCHES = 3. Each step is one forced-tool call decide whose schema is Decision(reasoning, action, query, url, summary, category, subcategory, sources, evidence, confidence); reasoning comes first. The floors are code, not prompt: a finish before any search is handed back once; when a hit's host contains the token or is a Wikipedia article about it, the page is fetched before a finish is allowed (own_page); a failed search backend is retried once without charging the budget; the evidence sentence must occur verbatim in a snippet or page (quoted_verbatim); confidence is capped at 0.6 when no source's title or host carries the token (names_the_token).

# weblookup/loop.py, INSTRUCTIONS (excerpt)
You find out what an unknown merchant is, by searching the web yourself, so a German
household's bank transaction can be categorized.
You are given a merchant token, the household's category list, and what your own earlier steps
returned. The token is the only thing about this household that ever leaves the machine: there
are no amounts, no dates, no account numbers and no names in it, and you must never put
anything into a search query that you were not given.
Call `decide` exactly once. You never answer in words: the decision is the answer.

Who calls it, and what the user sees

Three callers share one service (weblookup/service.py): the chat tool lookup_merchant, the categorizer at import (a deduplicated batch of the busiest unknown merchants, one-second pauses), and receipt headers (the store's name and category for a draft). Not query, chart, memory or statement extraction: the numbers invariant forbids web figures, and a statement page carries data that may not leave. Off by default per profile. Every request is journaled before it is sent and the journal is shown in Settings; results are cached per profile so a repeated merchant leaves nothing. The card shows the token, "1 search, 1 page read" with the page as a link, the quote and its source.

Measured (review of 2026-09-06 and ticket 53): on 20 merchants, lookups without a search went from 9 to 0 and pages read from 0 to 12 after the floors; the person rule stopped refusing 21 of 28 companies. Honest: the categorizer scored 96 percent with and without the lookup on the hosted model, so the gain is evidence and privacy, not raw accuracy. Demo with Vogtlandbahn or Combi, not Lidl.

The fine-tuned models: what QLoRA is and what we trained

Two special-purpose models are required. We trained QLoRA adapters for the query sub-agent and the chart sub-agent, on both local bases, and scored them against the vanilla bases with the product's own runtime.

LoRA and QLoRA in one picture

A LoRA (low-rank adaptation) leaves every weight matrix W of the base model frozen and learns a small correction B·A of rank r next to it. Only A and B are trained, so the trainable part is tiny: 34.9 million parameters for E4B (0.44 percent of 8 billion) at rank 16, 131 million for the 12B at rank 32. QLoRA keeps the frozen base in 4-bit NF4 during training, with bf16 compute, so a 12B fits comfortably on one GPU. The result is a 70 MB (E4B) or 262 MB (12B) file that llama.cpp attaches to the quantized base at inference without merging (llama_adapter_lora_init), scaled by alpha over r.

The training data: how it was generated

Training equals production: a sample is byte for byte the prompt the sub-agent sends, and a row is kept only when it executed.

flowchart LR H[5 synthetic households with truth files] --> W[60 Opus writers, quotas per household, language, kind, difficulty, lens] W --> G[execution gate: guard, database, second statement agrees to the cent, chart self-check on real rows] G --> R[headless render of every kept chart] G --> J[judges: figures recomputed from truth, reasoning held to the SQL's standard, pictures scored] R --> J J --> D[exact and near-duplicate sweep] D --> A[assembly: production prompt + wire tool call, plus repair and check-pass rows] A --> S[(query.jsonl 1,977 samples, chart.jsonl 1,791 samples)] style W fill:#1e2a44,stroke:#7aa2f7 style J fill:#1e2a44,stroke:#7aa2f7 style G fill:#2a2412,stroke:#f5b942
  • Households (scripts/generate_synthetic.py, fixtures/synthetic/households/): student (Leipzig, 300 bookings), family (Dortmund, 486), freelancer (Hamburg, 381), pensioner (Münster, 349), couple with two accounts (Stuttgart, 565), each deterministic with a truth file of merchants, categories and monthly totals. The shipped Berlin household is benchmark only.
  • Writers: each got a quota (90 query or 50 chart candidates, all households, half German half English, 40 percent difficulty 3, follow-ups over-weighted because they were the worst kind) and a lens (relative periods, subcategories, merchant spellings, rates and counts, recurring payments, income, comparisons, rankings, multi-turn chains). Writers never saw the benchmark. Each also wrote deliberate wrong attempts.
  • The gate (training/data/gate.py): the statement runs through the real guard against the household's database; a second statement the writer wrote differently must agree to the cent; degenerate results are dropped; chart code must pass the real self-check on the real rows first time. Every drop carries a reason. 1,968 query and 1,195 chart rows survived.
  • Judges: a second Opus pass per batch recomputed each figure from the truth file before reading the statement, held the reasoning line to the same standard as the SQL (keep, fix, drop, revise), and opened a fifth of the chart renders per shape. Disagreements were dropped, not argued.
  • Assembly (training/data/assemble.py): a kept row becomes the exact prompt the production builder makes for its household plus the target tool call as Gemma writes it on the wire; wrong attempts become repair rows (the finding, then the corrected answer) and check-pass rows (the judge prompt and its verdict), because the adapter serves those prompts too.

The benchmark: how we measure

One benchmark for three purposes: choosing the local models, validating the adapters, and catching regressions. It runs the production sub-agent path with the product's own runtime.

  • Sets (bench/sql-benchmark.json, chart-benchmark.json): 459 SQL questions and 302 chart requests a household really asks, German and English, eight kinds, three difficulties. Gold comes from reference SQL run through the guard on the shipped year (build_gold.py), never from a model.
  • Scoring (bench/finquery_bench/score.py): figure match means every gold figure appears in the returned rows to the cent and the result is not a dump (at most a few times the gold's row count); SQL valid; first attempt; for charts shape match (the expected shape or a listed alternative), columns map, language, drawn (the frame accepted the code).
  • The unit: run_query and run_chart, the same functions the chat's tools call, with the check pass and the self-check on. A 30-case end-to-end subset also runs the whole chat turn to catch routing loss.
  • Frozen split (bench/SPLIT_FROZEN.md): a third held out by a hash of the id per stratum; adding cases re-cuts, so the split was frozen before any training row existed. The shipped household's writer candidates grew the benchmark (307 SQL, 229 chart), so the benchmark household is unseen in training.
  • Runtime parity: on the cluster the same Q4_K_M GGUFs, wire formats and llama-cpp build as the laptop, one RTX PRO 6000 per job; a cluster number is a laptop number, only the seconds differ.
  • Resolution: about five points on 459 cases and six on 302; anything smaller is inside the noise, and the shipping rule says so.

Quiz: check yourself

Answer out loud first, then open the answer. A grader will ask two or three of these.

Where exactly is profile isolation enforced, and why is that better than a prompt rule?

In the SQL guard: every statement runs against a temporary view created per request with the profile id inlined, on a read-only connection. A prompt can be ignored; a view cannot return rows it does not contain.

Name the three context mechanisms the sheet asks for and the code that implements each.

Isolation: the profile-scoped temp view in query/guard.py. Selection: context.assemble with select_memories, the summary, recent turns and only applicable tools. Compression: needs_compression at COMPRESS_ABOVE = 0.6 and summarize by the fast model, with an editable divider.

Why compress at 60 percent rather than at the limit?

The summarizing model needs room of its own, and a single tool result can be large. Folding before the answer runs means the turn that crosses the threshold already runs small.

What may a distilled memory never contain, and why?

Figures and dates (unless the user states a rule), one-off orders, and names the user did not say. Figures go stale and a small model poisons itself with half-remembered numbers; numbers come from queries.

What makes something a sub-agent in FinQuery, technically?

A tool whose handler runs a second Pydantic AI agent with its own instructions and a forced ToolOutput schema, checks the answer with code, and returns data. The chat agent cannot tell it from a plain tool.

Why is reasoning the first field of every sub-agent schema?

The model commits to period, filters, sign and grouping before it writes SQL, and the check pass and the judges hold that line to the same standard as the SQL. A rationale at partial coverage measurably hurts, so it is enforced everywhere or not at all.

List what the SQL guard refuses.

Anything but one SELECT; any relation but transaction_view; schema prefixes; CASE expressions that invent categories; cents in the projection; a subcategory used as a category; more than eight LIKE terms; CROSS JOIN; statements over 1,500 characters. It adds a LIMIT of 200 and runs read-only.

What does the check pass do, and how much did it buy?

Code names degenerate results, then a forced-tool judge answers ok or revise with the intent in words, and the sub-agent rewrites once. On the same model it moved SQL figure match from 69 to 79 percent, without any training.

How does a chart get on screen, and where do the house rules live?

Plan pass picks shape, caption and the data question; the rows come through the query path; the code pass writes a JavaScript body over an allowlist; the self-check runs it on the real rows and sends findings back up to three times; a sandboxed iframe draws it. Palette, axes and square corners live in the frame, so stored cards restyle without regeneration.

What do we not claim about sub-agents, and why not?

The extra credit for a controller that continues without waiting. The turn survives a closed tab as a server task, but the chat agent awaits its tool result.

Why is a vision-language model not enough for ingestion? Name the two guards.

Under blur it invents digits. Verbatim: every amount and date must literally occur in the source. Reconciliation: opening balance plus bookings equals closing, to the cent. Flagged pages become review cards; nothing is written silently.

Which file types are claimed, how do Excel and Word get in, and what is out of scope?

PDF, images, text, CSV, XLSX, DOCX. Excel rows feed the CSV mapping engine with cell types kept; Word text takes the pasted-text path with the same guards. Audio is out of scope.

Exactly what leaves the machine on a web lookup, and in which order does the scrubber decide?

Only a merchant token, plus the model's own short search query checked by the same rule. Order: a legal form anywhere means business; then the given-name list refuses persons in either word order; then the two-capitalized-words rule. Never amounts, dates, IBANs or names.

What are the web loop's budgets and floors?

Four searches, three page reads. Floors in code: at least one search before a finish; a fetch when a hit is the merchant's own site or Wikipedia; a failed backend retried once for free; the evidence quote must occur verbatim in what was read; confidence capped at 0.6 when no source names the token.

Why did we make the floors code rather than prompt?

A strong model answered from memory and never searched; the elective wording needs a visited page. A prompt depends on the model, code does not.

What is a LoRA, what does QLoRA add, and how big are our adapters?

A low-rank correction B·A learned next to each frozen weight matrix; only A and B train. QLoRA keeps the frozen base in 4-bit during training. 70 MB per E4B adapter (34.9 M parameters, rank 16), 262 MB per 12B adapter (rank 32).

Why is the loss only on the completion, and what does the completion look like?

The prompt is about 3,000 tokens and the answer about 150; loss on the prompt teaches nothing we want. The completion is the wire form of the forced tool call: <|tool_call>call:run_sql{reasoning:..., sql:...}<tool_call|>.

What does "kept only by execution" mean for a training row?

The statement passed the real guard and ran on the household's database, a second statement written differently agreed to the cent, the result was not degenerate; chart code passed the real self-check on the real rows. Then a judge recomputed the figure from the truth file and judged the reasoning.

Why is the benchmark household unseen in training, and why is the split frozen?

The shipped household's candidates went into the benchmark; the five new households went into training. Adding cases re-cuts the hash split and could move a case into the held-out set after it seeded training, so the split was frozen before any training row existed.

Give the before-and-after numbers and the verdict for each adapter.

E4B query 62 to 78, ships. E4B chart 38 to 36 with drawn 85 to 72 on the contaminated run, rerun pending. 12B query 78 to 82, inside the noise. 12B chart running.

What bug made the 12B adapters look broken, and how was it found?

llama.cpp passes raw line breaks inside tool-call JSON; the fine-tuned model writes multi-line SQL, strict JSON refused it, every answer failed validation. Found by a probe that printed the raw tool-call stream; fixed by normalizing the arguments before validation.

Why did the quick evals point at the wrong epoch?

Thirty cases through transformers without a grammar is a different runtime and a sample too small to read a four-point difference. The reported number is always the full llama-cpp run.

Why does the 12B gain so little from the same data?

It already answers 78 percent of a hard set; the data was written around a 4B model's mistakes (follow-ups, relative periods), which the 12B mostly gets right already. Four points on 459 cases is within the resolution.

What are the three reversals to own?

Qwen3.5 9B chosen on memory, replaced by Gemma 4 12B after the cluster benchmark. Preference optimisation built, measured and removed for multimodal ingestion. "No dashboard" in the spec became a dashboard of guarded queries after the research note.
